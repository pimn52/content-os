# Execution Planner, Capability Profiles and Hybrid Compute

## Product responsibility

Translate product intent into an executable provider/runtime/configuration choice without leaking one model's limitations into the narrative or media model.

## Layering

```text
Narrative / Scene intent
and preliminary EditPlan
        ↓
Hybrid Asset Router
what visual/content route is needed?
        ↓
Execution Planner / Compute Router
which provider/runtime/config executes it?
```

The two routers are deliberately separate.

Both decisions belong before resource-intensive production. Post-generation measured timing can refine the same plan; it must not be the first feasibility check. Visual/source ineligibility returns to planning with reasons and explicit alternatives.

## Local-first Data + Hybrid Compute

Local-first governs creator data ownership and control. It does **not** require every heavy model to execute locally.

```text
Content OS
├─ Local Core
│  ├─ Assets
│  ├─ IP / Project state
│  ├─ Evidence / QA
│  └─ Render / control
└─ Compute
   ├─ Local providers when suitable
   └─ Explicit approved remote/BYOK providers when needed
```

There is no hidden cloud fallback. Remote media transfer, cost and privacy implications must be explicit.

## Capability profile

Capability evidence belongs to a concrete:

> provider + model/version + runtime + machine/profile

A profile may record:

- capability type and local/remote mode;
- readiness;
- verified operating bounds;
- optional feature support;
- quality/continuity evidence;
- latency and resource observations;
- cost;
- license/commercial status;
- provenance and verification time.

Evidence from one machine does not silently become another machine's verified result.

## Purpose-scoped admission — record/resolver and fail-closed scope foundations

[D029](../../DECISIONS.md#d029--admit-execution-for-an-evidenced-purpose-and-preserve-that-scope-downstream) allows the normal workflow to validate R1 internally when current, exact license evidence permits the intended activity. The inert provider-neutral admission service now stores operator-adopted project receipts and offers a pure scope decision. Current normal dispatch still requires commercial-safe admission; evaluation is not integrated into execution. Existing provider schemas/quality profiles are not relabelled; no real provider is admitted by this code acceptance.

The frozen inputs are execution purpose, project, exact capability/configuration/model-artifact identity, trusted use-admission receipt and current evidence, dependency restrictions, and operation. `commercial_production` is the compatibility default; `internal_evaluation` must be explicit on a new Run. A project-scoped versioned ProviderUseAdmission binds operator, purpose, actual intended activity, license source/version/local evidence hash, exact identity/configuration digest, permitted local generation/derivation/review/download and revocation state. It is distinct from capability evidence and the existing Run budget/call authorization. Its issuer is an explicitly configured execution-admission operator; a Talking-source reviewer is not automatically such an operator. Evidence is resolved under the configured data root. A record of asserted permission alone cannot prove the terms apply.

| Case | Required decision after migration |
|---|---|
| Omitted purpose / legacy commercial lane | Preserve existing commercial-safe and evidence checks; never infer evaluation |
| Explicit internal evaluation, current trusted receipt permits the exact use, exact capability verified | Eligible only within supported local lane; all ordinary source/consent/budget/QA/review gates still apply |
| Non-commercial label or operator assertion with missing/incompatible underlying terms | Block use admission; internal product development is not presumed permitted |
| Missing capability, license evidence, project match or model/configuration identity | Block with the specific missing evidence; no automatic promotion from an old asset review |
| Revoked/stale receipt, changed evidence/weights/configuration, stripped origin or mismatched purpose | Block fresh dispatch/resume/repair/consumption; retain historical work |
| Evaluation dependency in a commercial Run or attempted purpose change | Block; a new ID/copy/reimport cannot remove the restriction |
| Complete QA/human approval under evaluation | Quality evidence stays valid for its exact subject; permitted use remains evaluation |
| Fixture authority or unsupported remote/public evaluation operation | Never live admission; return a named unsupported/missing-authority state |

One resolver owns this decision. Run/Job fingerprints and Worker receipts pin purpose/admission; before durable reservation, Worker validates and freezes the actual selected provider/model artifacts/runtime/machine/configuration for its prepared invocation. Model loading follows reservation; preflight must not claim loaded-weight evidence. Downstream composition, Talking preview/admission, repairs, rendering and commercial-consumption checks retain effective ancestor restrictions. Current revocation is rechecked without rewriting the original evidence. No new inference budget is charged merely to inspect or admit completed bytes. Do not enable evaluation until this propagation is complete for the supported lane.

Existing real configuration evidence can be explicitly adopted once when complete, avoiding another full calibration campaign; unknown fields remain gaps. Normal users see purpose, missing evidence and permitted next action, while operator setup retains the underlying evidence details. Live Worker readiness, adequate scene duration and exact new-copy QA remain separately observable requirements.

Current APIs under `/projects/{id}/` are `GET/POST provider-use-admissions`, `GET provider-use-admissions/{admission_id}`, `POST provider-use-admissions/{admission_id}/revoke` and diagnostic `POST provider-use-resolution`. Write actions use `x-content-os-execution-admission-key`, independently resolved through `CONTENT_OS_EXECUTION_ADMISSION_KEY_HASHES` (actor→unique SHA-256 of a high-entropy key, at least32 characters). General API access and Talking-review role do not substitute. Operator adoption takes only an idempotency key, portable review reference and expected hash; actor/time/report are bound by the service. Requests cannot type an actor, permission or commercial flag around the gate.

## Advanced Settings

Advanced Settings is the expert override surface over the same resolution system.

It should:

- expose provider-owned parameters through a common product pattern;
- show value provenance such as verified / provider default / user override / unknown;
- allow narrow-scope overrides and reset-to-auto;
- preserve hard consent, budget, license, provenance and runtime-integrity gates;
- never auto-promote a successful user tweak into a global default.

Narration performance intent is **not** an Advanced Setting. It is an
exact-copy-bound editorial plan for emphasis, pace, pauses and rhythm. A
provider schema must separately expose whether it can apply that plan; an
unknown feature stays unknown even when the provider has a numeric `speed`
parameter. Only an explicit adapter application receipt, followed by Voice QA
and U-Voice review, can establish a performance result.

Its derived Delivery Plan is likewise pre-execution structure, not a request
to create a duration, silence or provider-specific control. Execution may only
use it through an admitted adapter with explicit feature support.

## Product boundaries

### Bounded Voice repair accounting

Run-scoped whole-take Voice replacement shares the original `repair_allowance` with existing Talking and presentation records, rather than creating a fresh retry budget. Atomic submit preserves predecessor Job/audio/QA snapshots. Worker reservation separately caps one local TTS and one local QA ASR operation; retry attempt numbers or new call keys do not reopen either limit. Project/global provider budgets still apply. External charge authority is zero; local compute and user-active time remain unknown. Ordinary non-repair historical reservations retain their existing semantics.

Normal Run Voice dispatch saves profile/reference/capability/payload and persisted-setting evidence. Configured Voice Workers record an execution receipt at reservation. For the optional local OmniVoice Worker, `CONTENT_OS_VOICE_RUNTIME_ID` and `CONTENT_OS_VOICE_MACHINE_ID` identify its configured scope; the receipt also records runtime Python path, steps, speed and timeout. Missing IDs do not affect ordinary evaluation but cannot authorize later repair. Local Voice QA uses `CONTENT_OS_VOICE_QA_RUNTIME_ID` and `CONTENT_OS_VOICE_QA_MACHINE_ID`; its matching admitted ASR capability's `verified_parameters` must equal the actual device, compute type, VAD/word-timestamp flags and silence thresholds. The repair Worker compares these fields before reserving. These identities/configuration receipts are not commercial or physical-hardware certification and do not admit evaluation-only weights.

Legacy Jobs without original snapshots/receipts stop; no compatibility backfill invents prior configuration. Multiple or absent eligible ASR profiles stop rather than selecting by sort order. A persisted verified capability is not a live Worker heartbeat: the plan labels live readiness unobserved, and the ordinary queued Job can wait for a configured Worker. Remote/unknown ASR locality, missing accounting, revoked/changed authority or changed bytes fail before repair inference. No live-provider or measured cost/time evidence is claimed by the offline contract tests.

### Bounded presentation revision accounting

An exact completed-render observation can propose a supported presentation-only revision without generating Voice or Talking. Explicit apply shares the creation-bound allowance above, preserves the predecessor and enqueues one new ordinary Render Job. Its Worker reserves at most one durable `local-render`/`remotion-ffmpeg` operation, rechecking current inputs, approval/admission and project/global budget before execution. New keys/retries do not grant another render reservation. Successful technical evidence records the exact new output hash and measured streams/decodability, with external charge zero and local compute unobservable. Failure retains its accounting/evidence and does not automatically retry inference or admit an output; final U-Product remains required. This path is backend/synthetic evidence, not normal UI or real creation repeatability.
